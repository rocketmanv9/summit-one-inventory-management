# PO Approvals audit — the Zach case (2026-08-12)

Sprint item 14. Traced the full submit → route → notify → decide pipeline on
stage to explain why Zach's purchase "disappeared into the ether," and fixed the
structural gaps that made it invisible.

## The incident

- PO **26-0047** (`54c4620b-edee-40a8-b7b9-caab8912a8c2`), created 2026-08-11
  20:16, delivery location **Kingston**.
- `created_by_user_id` = Zach (`4875fb2f-…`, zkauffman@acmoate.com).
- `origin` = `auto_reorder`; notes "Auto-generated by nightly reorder (run
  20260811)"; `approval_reason` "AI restock draft — nightly reorder (run
  20260811)".
- `approver_user_id` = **NULL** → routed to the anonymous admin pool.
- Approved by **Sean Krause** (admin) at 21:23, silently — no captured reason.
- Grant "never saw anything to approve/deny."

## Root causes

### 1. Provenance mislabel — a machine PO wore a human's name

`origin='auto_reorder'` is correct: 26-0047 was created by the nightly cron
`supply_chain.rpc_generate_reorder_pos_v2`, **not** by Zach tapping anything.
The cron runs with no auth session, so it needs an author for the row. Its
author-selection was:

```sql
-- Machine-created rows still need an author; reuse the most recent PO creator.
SELECT po.created_by_user_id INTO v_fallback_user
FROM supply_chain.purchase_orders po
WHERE po.tenant_id = p_tenant_id AND po.created_by_user_id IS NOT NULL
ORDER BY po.created_at DESC LIMIT 1;
```

Zach happened to be **the last human to create a PO**, so the nightly job
stamped his id into `created_by_user_id`. The approvals inbox card renders
`{buyer_name} wants ${total}` → it read **"Zachary Kauffman wants $X"** for a PO
Zach never touched. That is the "did he tap a button?" smell: he didn't; the job
misattributed itself to him.

**Fix:** machine-authored reorder POs now carry `created_by_user_id = NULL`. The
"most recent human creator" is still used as a **routing input** (so the
resolver has a supervisor/location to key off) but is no longer written as the
author. The inbox + PO detail render `origin='auto_reorder'` + null author as
**"Nightly auto-reorder"**, never a person.

### 2. Routing left no trace — the pool was invisible

`resolve_po_approver()` returned a single uuid or NULL. NULL means "any admin,"
but nothing recorded **why** it resolved to nobody, and a pool PO looked
identical to one routed to a named person. For 26-0047 the real chain was:

1. Kingston has **no** `po_approver_user_id` (all 8 locations are NULL — there
   was no settings UI to set one until item 10).
2. Zach has **no** `hr_person_id` link, so the supervisor step can't even start
   (and org-wide, **177 of 210** active people have no
   `supervisor_hr_person_id`).
3. → admin pool, `approver_user_id = NULL`.

**Fix:** new `supply_chain.resolve_po_approval_route()` returns the resolved
approver **and** a structured trace:

```json
{
  "resolved_rule": "admin_pool",
  "resolved_user_id": null,
  "steps": [
    { "rule": "location_override", "outcome": "none",
      "detail": "Kingston has no approver configured" },
    { "rule": "supervisor", "outcome": "none",
      "detail": "buyer is not linked to an HR person" },
    { "rule": "admin_pool", "outcome": "matched",
      "detail": "routes to the admin pool — 5 admin(s) can approve, nobody specific" }
  ]
}
```

It is stored in a new `purchase_orders.approval_route` JSONB at submit time by
all three PO-creating paths (`rpc_create_purchase_order`,
`rpc_submit_po_for_approval`, `rpc_generate_reorder_pos_v2`).
`resolve_po_approver()` is preserved (mobile item 09 + the simulator call it) and
now delegates to the route resolver, so there is exactly one precedence
implementation.

### 3. Why Grant's inbox "showed nothing"

Grant **is** an admin, and the approvals GET route already shows admins **every**
`awaiting_approval` PO (no `approver_user_id` filter for admins) — so 26-0047
*was* technically visible in his pending inbox. What was missing was any signal
that it was **unrouted/anonymous**, plus there is no push/notification wired
(out of scope here). The PO sat in a pile of pending items with no loud "this one
is in the ether — nobody specifically owns it" marker, and another admin (Sean)
cleared it before Grant looked. So "showed nothing" = no distinguishing signal,
not a filter bug.

**Fix:** the routing visual renders the admin pool as a loud amber ⚠ node
("Admin pool — nobody specific / Unrouted") with an inline "Configure approvers"
link, on both the inbox rows and the PO detail. Pool POs are now unmissable.

### 4. Approve captured no reason

Deny required `rejected_reason`; approve captured nothing. Sean's approval left
only the pre-filled AI label. Added `purchase_orders.approved_reason` (mirror of
`rejected_reason`). The **web UI now requires** a reason on approve (short
presets + free text), same as deny. The API keeps `reason` **optional** on
approve for mobile compatibility (item 09 doesn't send one yet).

## What shipped (item 14)

- Migration `20260812000002_po_approval_route_provenance.sql`:
  - `approved_reason TEXT`, `approval_route JSONB` columns.
  - `resolve_po_approval_route()` (approver + stepped trace); `resolve_po_approver()`
    delegates to it.
  - Route stored by all three PO-creating RPCs.
  - Reorder generator: machine POs get `created_by_user_id = NULL`.
  - `inventory.purchase_orders` view exposes the new columns.
- `POApprovalTrail` component — the requested → routed → decided pipeline with
  the loud pool ⚠, rendered on the approvals inbox rows and the PO detail panel.
- Approve-with-reason in the web approvals inbox; reason stored in
  `approved_reason` and shown in the Approved tab + on the PO.
- Config-health header on `/settings/purchase-approvals`: location-approver
  coverage (0/8) and supervisor coverage (33/… with 177/210 org-wide gap made
  loud). The inline per-location approver editor + simulator already shipped in
  item 10.

## Not fixed here (by design / out of scope)

- HR-side supervisor data entry (surfaced the 177/210 gap; don't edit HR data).
- Push notifications on new/pool POs.
- The routing **order** itself (location → supervisor → admin) is unchanged.
- Backfill of `approval_route` on historical POs (only 26-0047 was backfilled as
  the demo exemplar).
